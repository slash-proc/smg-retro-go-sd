## Constraints in the current GWRG processor ABI

The current ABI's `alloc(len: u32)` and `input_add(ptr, len)` require the host
to place each whole input in WASM linear memory. A 4,699,979,776-byte ISO is
larger than the largest length representable by `u32`, before accounting for
the module's other memory. WASM linear-memory limits and project memory caps
make a full copy impractical even on browsers with ample disk.

The ABI also requires converters to have no imports. That rules out direct
filesystem calls from WASM, but it does not rule out a host-mediated range
protocol: the module can yield a read request through exports, let the Worker
read `File.slice()`, then resume after the Worker copies the requested bytes
into WASM memory. Merely using `File.stream()` does not solve this because it
is sequential; the extractor needs random access. Nod's synchronous read API
will also need an async/resumable adapter for this request/response flow.

## Chosen direction: host-mediated range reads

The primary path will read ranges directly from the selected browser `File`.
WASM yields a request containing an input id, 64-bit file offset, and bounded
length. The Worker reads that range with `File.slice()`, copies it into a
bounded WASM buffer, and resumes the converter. This avoids both an ISO-sized
WASM allocation and a second 4.38 GiB browser-storage copy. A bounded range
cache can coalesce nearby reads and reduce host round trips.

This keeps the processor import-free: the exchange uses WASM exports and
linear memory, with the host retaining control of the `File`. It does require
an async/resumable adapter around nod's currently synchronous disc reads. A
step can return “needs input” without failing; the host supplies the range and
then calls the next step. Browser `File.stream()` alone is not sufficient,
because disc files and Wii partitions are read by seekable offsets rather than
one uninterrupted sequence. The nod adapter keeps its parsed disc and
partition readers alive across host range requests, resumes the current file
read after each supplied range, and hashes file bytes incrementally. It retains
bounded range caches for random-access metadata and sector reads.

OPFS remains a fallback for browsers where direct range reads prove unreliable.
It can also hold the converter's extracted files and construction intermediates
without loading the full 243.5 MiB source set or roughly 148 MiB construction
tree into WASM memory. The final asset set is about 66.2 MiB. If output remains
hundreds of files, those can be streamed to host storage as well.

### Shared requirements

Whichever input option is chosen, the converter should read disc metadata and
only the manifest-selected paths, decrypting the Wii data partition as nod
does, without expanding the whole disc into a directory. Write extracted
working files and construction intermediates to converter-owned scratch
storage, retaining only the active file and algorithm working set in WASM
memory. Remove temporary files at completion unless the user chooses to
preserve a resumable conversion.

The source and output sizes show why the converter should not stage every
intermediate in RAM. The 243.5 MiB extracted input set and roughly 148 MiB
construction tree already approach or exceed typical converter memory caps,
while the final asset set is only about 66.2 MiB. Disk-backed intermediates and
one-file-at-a-time processing are the important memory reductions.

The pinned nod reader (`2.0.0-alpha.9`) has now been exercised natively against
the supplied ISO. It found all 596 selected data-partition files, read the DOL
from partition metadata, and matched all 597 inputs byte-for-byte with
`build/orig` (261,599,168 bytes total).

## Range-input ABI extension

The shared processor ABI now defines optional `processor.extensions["range-input"]: 1` while
keeping `processor.version` and `abi_version()` at 1. The original v1 format and export set are
unchanged when `extensions` is absent. Hosts reject unknown extensions before fetching or
instantiating a converter.

For range-enabled converters, `input_stream_add(size_lo, size_hi)` registers a file by its 64-bit
size. During `run_step`, status 2 yields an input handle, 64-bit offset, bounded length, and a
WASM destination pointer. The host reads that range from the selected file, copies it into WASM
memory, and resumes with `input_supply`. The protocol is export-based and adds no WASM imports.
Each request is capped at 256 MiB. Strict variant hashing still happens in the host, in bounded
chunks, before the module runs.

GWProv implements the extension using seek/read on local files. The GNW web-builder keeps the
browser `File` in a Worker and services requests through `File.slice()`. Its input gate hashes a
Blob in 8 MiB chunks. Both consumers preserve the old whole-file v1 path for tools without the
extension, and reject unsupported extension versions.

The converter still returns outputs through the original output pointers. No streamed-output
extension or scratch-file protocol has been added. For this homebrew, the converter's target is
one `smg_assets.xip` output (31,084,812 bytes); `SMG.bin` and `smg_code.xip` are already built
from project code. The 66.2 MiB figure is the raw generated asset corpus before linker packing.
The XIP must match the native link layout exactly because the prebuilt core contains linker-derived
relocation-site offsets into it. This output fits the base ABI's pointer model, but conversion
intermediates still need to stay within the published memory cap.

## Browser converter implementation slice

`tools/wasm_converter/` contains an import-free WASM identity verifier and a
static Pages-style browser UI. The verifier checks the exact USA image size and
`RMGE01` disc ID, then hashes the complete image in configurable 64, 128, or
256 MiB host-mediated ranges against SHA-1
`a36105c9fbfff6041dc5babf4318c6a216ad470a`. Its linear memory is bounded by
the selected input window plus small state; it never stores the ISO in WASM or
OPFS. The browser Worker owns the `File` and supplies each requested range.
The selected range also exists transiently in browser memory while it is copied
into WASM, so peak memory is approximately twice the chosen chunk size plus
runtime overhead. These sizes need about 65, 129, and 257 MiB of WASM linear
memory, plus the temporary browser copy. They reduce host/WASM exchanges to
about 71, 36, and 18 ranges. Every setting still hashes all 4.7 GB, so chunking
reduces exchange overhead rather than the amount of SHA-1 computation.

The 64 MiB WASM setting was run through a Node host adapter against the
supplied ISO: it processed all 4,699,979,776 bytes, reported zero imports, and
matched the expected SHA-1. The 128 and 256 MiB allocations were also confirmed
to grow WASM memory to about 129 and 257 MiB. The original 1 MiB run exposed
and fixed JavaScript's signed conversion of the low half of a WASM `i32` when
assembling offsets above 2 GiB.

The headless browser benchmark in `tools/wasm_converter/browser-test/` follows
the Playwright 1.63 Docker setup used by `../gnw-web-builder/tools/device-test/`.
With the module capped at 320 MiB, Chromium 153 completed identity verification
at 64/128/256 MiB in 17.95/18.44/17.42 seconds. Firefox 155 took
22.30/20.57/20.08 seconds. All six hashes matched. These are measurements of
the latest run, not fixed performance guarantees.

The `smg_asset_converter.wasm` build exposes the GWRG processor ABI v1 plus the
optional range-input v1 exports. Its `run_begin`/`run_step` path drives a
nod-based selective extraction stage. The module has no imports. The regular
8 MiB build and benchmark-only 64/128/256 MiB builds declare a 1,024 MiB
maximum. The browser page selects among these variants, while GWProv uses the
regular 8 MiB module. The 1 GiB maximum is a growth ceiling; the completed
8 MiB conversion currently reaches 356.7 MB of linear memory. It returns one
`generated_assets.pak` intermediate, not an installable converter.

The extractor's `DiscStream` adapter requests aligned input windows and returns
a resumable `WouldBlock` when a range is missing. It keeps the nod disc and
partition readers alive across requests, traverses dependency-prioritized groups
in physical disc order, and checks SHA-256 incrementally against `sources.txt`. Metadata ranges
remain capped at 16 MiB. The file cache keeps at most two input windows and
evicts before copying a new range, preventing alternating reads from thrashing
and avoiding an extra full-window allocation. The 256 MiB variant keeps one
file-cache window to avoid duplicating another full input buffer. Large windows align on 64 MiB
boundaries so nearby reads can reuse the same fetched bytes. `main.dol` is read
from partition metadata, outside the FST. The release profile uses `opt-level =
3`; the prior size-optimized profile exceeded GWProv's fuel ceiling.
